# 方案：「进行中的事」缓冲区 + 粘性通知（前缀冻结与上下文整理）

日期：2026-09-17
状态：**待用户确认后开工**（用户要求先讨论定稿）
需求来源：用户提出的「缓冲记忆区」想法，经多轮讨论定稿（见对话记录）

---

## 0. 一句话设计

> **前缀四块（外壳 / 工具手册 / 记忆 / 状态）只在「窗口回落流程」里重建；其余一切变更都以「追加到会话尾部的通知」表达。**
> 两次合并之间，提示词前缀逐字节不变 ⇒ 全程命中缓存；回落点付出的一次未命中，同时完成「缓冲区更新 + 快照刷新 + 窗口裁剪」。

分层定位（用户拍板）：

| | 判据 | 谁写 | 出口 |
|---|---|---|---|
| 长期记忆 | 一直成立的事实/偏好 | 模型抽取(write_memory) + 用户手改 | 永久 |
| **进行中的事（缓冲区）** | 一段时间内成立、会过期 | 模型压缩时改写 + 用户手改 | 完成→归档（不删除）；可一键存入日记/记忆 |
| 日记 | 发生过什么（流水） | 用户 + 记录兜底 | 永久 |

### 1.1 新表 `buffer_items`（DB version 8 → **9**，加迁移）

    val status: String = "active",   // active | archived

`BufferItemDao`：`all()`, `active()`, `byId()`, `upsert()`, `setStatus()`, `delete()`, `clearAll()`, `insertAll()`（后两个供备份恢复）。
`BufferRepository` 包装。

### 1.2 冻结快照 `filesDir/prefix_snapshot.json`

**这是本方案的关键新增状态。** 现在 `runTurn` 每轮现读 `memoryRepository.memoryContextText()`，一改记忆前缀立刻断；要做到"零前缀变化"，注入文本必须**存下来，只在合并点刷新**。

```kotlin
@Serializable
data class PrefixSnapshot(
    val memoryText: String = "",   // [2] 注入文本
    val bufferText: String = "",   // [3] 注入文本
    val savedAt: Long = 0L
)
```

`PrefixSnapshotStore`：`load()`（缺失返回 null）、`save()`、`rebuild(memory, items)`（从 DB 重渲染）。
- 数据库仍是**页面**的真相；冻结的只是**注入**那一份。
- 升级首次启动：文件不存在 ⇒ 从 DB 渲染一次（文本与旧行为一致，不额外断前缀）。

### 1.3 水位线（压缩覆盖到哪一轮）

`StoredChat` 加 `coveredThroughTurnId: Long = 0L`（随会话快照持久化）。

- 语义：**已折进缓冲区的最大轮 id**；`0` = 一条都没覆盖。
- 压缩输入 = `id > coveredThrough` 且已离开窗口的轮。
- 好处：① 压缩失败/放弃不阻塞，这批下次一起补（自愈）；② 不重复压缩；③ `chat_session.json` 60 轮上限给了约 40 轮余量。

### 1.4 变更通知（notices）

- **存放**：`Session.Turn` 加 `notices: MutableList<String>`（**不放 `assistant` 里**，否则 `replaceLastAssistant`/`clearAssistant`（重做）会把它清掉 → 变更信息静默丢失）。
- **产生**：用户在前端改动（记忆增/改/删；缓冲区增/改/归档/取消归档/删除）。
- **形式**：追加到**当前最后一轮**，如
  `[系统] 用户手动更新了「进行中的事」：#7 已归档，请勿再使用快照里的这条。`
- **渲染**：`Turn.messages()` 在本轮 assistant 消息之后渲染为 `ChatMessage("user", text)`（沿用工程既有的 `[结果]` 回传惯例）；**不产生 UI 气泡**。
- **铁律**：**只能追加，之后永不重写/重排/重新渲染**。若每轮把"待合并变更"拼在对话最后，位置逐轮后移 ⇒ 每轮都多付「一轮对话 + 通知」的未命中。
- **无轮可挂**（会话为空）⇒ 不落通知，直接合并快照。
- **清除**：合并时统一 `stripNotices()`（此时前缀本来就要重建，免费）。

## 2. 注入布局与渲染规则

```
[0] system  外壳 + 用户设定                       （冻结：只在用户改提示词时变）
[1] system  工具手册（含 update_buffer 契约）+ 日记标签
[2] system  记忆块（冻结快照）
[3] system  用户当前状态（进行中的事）（冻结快照；空则整块不插入）
[4..]       对话尾部（每轮内 notices 渲染在本轮消息之后）
```

`[3]` 的固定文案（写在块首，防陈旧误用与自我确认漂移）：

```
用户当前状态（进行中的事）：
以下是你在**这段对话之前**整理的用户状态（背景，不是用户刚说的话）；若对话中已有更新，以对话中的最新说法为准。
这些内容可能已过时（见每条后面的"更新于"日期），不要当作一定还成立的当前状态。
#id=7｜在办｜零差探测器搭建｜更新于 2026-09-16
已完成：…；待办：…；关键数据：…
相关日记：#id=252、#id=260
```

**渲染规则（渲染器必须是纯函数：数据 → 文本，不含任何随时间变化的东西）**：

1. 只渲染 `status = active`；按 `id` 升序（**不按 updatedAt 排序**，否则一更新就换位置）。
2. 日期**绝对**（`更新于 2026-09-16`）；**绝不写"3 天前"**——相对天数每天变 = 前缀每天断。相对天数由界面算给人看。
3. 引用日记一律用 `#id=123` 写法（`ReadDiaryTool` 的注释实测过 `#123` 会被模型和日期/标签看串）。
4. **硬上限**：`buffer_inject_char_limit`（默认 1200 字）、`buffer_inject_max_items`（默认 15）。超限按"最近更新"优先保留，块尾追加
   `另有 N 条更早的状态已省略（可在「进行中的事」页查看）`。**数据一条都不删**（用户手动管理，不做自动 TTL）。
5. 悬挂日记 id：合并/写入时用一次 SQL 校验存在性，丢掉已删的 id（不让模型判断）。

### 2.1 prefixSignature

`agent.cachePrefixSignature(memoryText, bufferText, diaryTags)`，覆盖 `[0][1][2][3]`。

- 提示词/标签/手册变化 ⇒ 立即生效 + 保留现有回落行为（v1.7.2 的决定）。
- **合并引起的变化不触发回落**：合并后立刻 `session.markPrefixSignature(newSig)` 重置基线。回落由窗口条件驱动（压缩点通常两者同时发生，只付一次未命中）。
- 冷启动有待合并变更 ⇒ 合并（前缀无论如何要断，早付早好）；**没有待合并变更则什么都不做**。

## 3. 时序：`runTurn` 重构

```kotlin
1. session.enforceImageRetention(imageRetention)
2. snapshot = prefixSnapshotStore.load() ?: rebuildFromDb()      // 冷启动兜底
3. sig = agent.cachePrefixSignature(snapshot.memoryText, snapshot.bufferText, diaryTags)
4. plan = session.planWindow(minTurns, maxTurns, charLimit, sig)  // 只读
5. if (plan.trigger != NONE || (冷启动 && session.hasNotices())) {
       a. 若 bufferEnabled && 待压缩批次字符量 ≥ buffer_compact_min_chars → compactContext(...)
          （失败 ⇒ 不阻塞回答，聊天里留可操作提示，见 4.4）
       b. merge()：snapshot = rebuildFromDb()（记忆 + 缓冲区重渲染）；session.stripNotices()；持久化
       c. sig = 重算；session.markPrefixSignature(sig)
   }
6. ctx = session.buildContext(min, max, charLimit, sig, plan)      // 执行裁剪；原因标签见下
7. agent.route(...) → 正常回答（既有流程不动）
```

**顺序是硬性要求**：合并**必须先于裁剪**。`planWindow` 返回将被丢弃的轮，压缩要用它们；而一旦 `buildContext` 执行 `trimTo`，这些轮就从 `Session` 里物理消失了（只剩快照文件里一份）。

### 3.1 `Session` 改造

```kotlin
enum class WindowTrigger { NONE, PREFIX, MAX_TURNS, SOFT_CAP }

data class WindowPlan(
    val trigger: WindowTrigger,
    val reason: String?,        // 展示用文案
    val willDrop: List<Turn>,   // 即将离开窗口的轮（压缩输入依据）
    val keptTurns: Int
)

fun planWindow(minTurns, maxTurns, softCharLimit, prefixSignature): WindowPlan  // 只读，不改状态
fun buildContext(min, max, soft, prefixSignature, plan: WindowPlan? = null): BuiltContext  // 执行裁剪
fun markPrefixSignature(sig: String)   // 合并后重置基线
fun appendNotice(text: String)         // 追加到最后一轮（无轮则忽略，由调用方决定立即合并）
fun hasNotices(): Boolean
fun stripNotices()
```

新增回落原因常量：`RESET_COMPACTED = "上下文已整理"`（压缩轮用；此时通常同时触发了轮数/字符原因，展示以"已整理"为主）。

## 4. 压缩轮

### 4.1 请求构造（同一链路，最大化缓存命中）

```
messages = PromptBuilder.buildChatMessages(
               memoryText = snapshot.memoryText,
               bufferText = snapshot.bufferText,
               conversation = 当前窗口的全部轮（不含刚开始的这一轮，避免连续两条 user、也不诱导它回答），
               toolManual, diaryTags)
           + ChatMessage("user", TRIGGER)
```

**必须与上一次请求逐字节一致**：不裁剪、不剥离图片（用户裁定：图片 token 是命中价，跟整段未命中不是一个量级）、不改手册。这样从 `[0]` 到窗口最后一轮**全部命中**，只有 TRIGGER（几十字）按未命中计价。

```
TRIGGER = "【上下文整理】你看到的对话中最早的 N 轮（自 [yyyy-MM-dd HH:mm] 起）即将离开上下文。
请调用 update_buffer 把它们整理进「进行中的事」。有变化的改写、已结束的归档、未变化的原样保留；
不要回答用户的问题，不要输出任何解释文字。"
```

`【上下文整理】` 是**只在这种情况启用的标记**（正常轮永不出现 ⇒ 不污染前缀）。压缩轮**不写入会话历史**、不产生 UI 气泡。

### 4.2 调用与解析

- 非流式：`Agent.chatOnce(messages, Capability.CHAT, maxTokens = 2048)`（薄封装 `ProviderRegistry.chatCompat` + `thinkingParamsFor` + `effortSafeCall`）。
- 解析复用 `ToolRegistry` 的 `[调用] {json}` 行解析与分发（若相关函数为 private，提为 internal）。
- **最多 2 轮**（模型可能先要求读点什么），防死循环。非压缩轮禁止 `update_buffer`（见 4.3）。
- 成功 ⇒ `coveredThroughTurnId = max(批次轮 id)`。
- 用量**单列统计**，不进"最近一轮对话"合计。

### 4.3 `update_buffer` 工具（进手册 = 永久免费，且契约只写一遍）

- 注册进 `ToolRegistry`，**手册里可见**；压缩要求（保留什么/改写什么/归档什么/输出格式）全部写在 `description` 里，尾部 TRIGGER 只需一句。
- description 里写死：**「你绝不能主动调用这个工具，只有在收到以【上下文整理】开头的指令时才调用。」**
- **应用侧硬拦截**（第二道保险）：`execute` 检查"当前是否处于压缩轮"标记，不是就返回 `ToolOutcome.Failure("这个工具只能在上下文整理时调用")`。误调用只浪费一轮，不损坏数据。
- 参数：`items[{id?, kind?, title, body, diary_ids?}]`（带 id = 改写；未变化的条目不要出现在这里）、`archive_ids[]`、`delete_ids[]`。
- 返回里带上被改写/新增条目的实际 `#id=`，便于模型后续引用。

```kotlin
class UpdateBufferTool(
    private val bufferRepository: BufferRepository,
    private val inCompactionRound: () -> Boolean
) : AssistantTool
```

### 4.4 失败处理（**绝不阻塞回答**）

- 失败 ⇒ 照常发出主请求、照常回答；同时在聊天里留一条**可操作提示**：
  `📦 上下文整理失败，最早 N 轮尚未归档。 [重试] [放弃]`
- **重试** = 立即再跑一次（缓存还热，几乎免费）。
- **放弃** = 水位线推进到这批（视为已放弃，不再重试）。
- 不推进水位线时，这批内容仍留在 60 轮快照里，下次压缩自动带上（自愈）。
- （说明：用户原话"让用户选择重试还是放弃"；这里做成非阻塞提示而非模态弹窗，避免为整理失败挡住回答。若用户要求模态，改一行即可。）

## 5. 手动改动路径（记忆 / 进行中的事）

| 动作 | 处理 |
|---|---|
| 记忆页 增/改/删 | 写 DB（页面立即反映）+ `appendNotice("[系统] 用户手动更新了长期记忆：…")`；有会话可挂 ⇒ 通知；无轮 ⇒ 立即合并快照 |
| 进行中的事页 增/改 | 同上（`source = "user"`） |
| 进行中的事页 归档/取消归档/删除 | 同上，通知文案写硬：`#12 已删除，请勿再使用快照里的这条` |
| 设置页 提示词/标签 | **立即生效**（前缀本身在改，无法用变更行表达），保留现有回落行为 |
| 存入日记（按钮） | `DiaryRepository.addEntry(source="buffer")`，成功后默认同时归档该条（可取消） |

**代价**：手动改动**零前缀变化、零额外未命中**；改动本身立即可见（通知行），进快照最多滞后一个窗口周期（约 15 轮）或一次冷启动。

**澄清**（用户已确认）：删除/归档类**与新增同样走通知**，不做立即合并。

## 6. 与既有机制的交叉改动

1. **保留天数第三条件**（必须）：`expiredTurnIds(turnCreatedAt, contextTurnIds, cutoff, coveredThrough)` 增加 `&& id <= coveredThrough`。
   不加会出现"**压缩还没覆盖到、保留天数先把原文删了**" —— 内容永久消失。
2. **清空对话**：确认弹窗加勾选项「同时把要点整理进「进行中的事」」（默认勾上）；不管勾不勾，都执行 `merge()`（刷新快照 + 清通知）；不勾则不压缩。水位线归零。
3. **冷启动恢复**（`restoreSession`）：载入快照；快照缺失 ⇒ 从 DB 重建；`hasNotices()` ⇒ 走一次合并。
4. **持久化**：`StoredChat` + `coveredThroughTurnId`；`StoredTurn` + `notices`（默认空，向后兼容）。
5. **会话条数上限**：通知不占"轮"，但计入 `charWeight()`（会推高字符软上限，触发点同时是合并点，自愈）。

3. `NoticeTest`：通知渲染在轮内固定位置、`replaceLastAssistant`/`clearAssistant` 不影响通知、`stripNotices` 清空。
4. `UpdateBufferGuardTest`：非压缩轮调用被拒（Failure）；压缩轮可写；id 改写/新增/归档/删除行为正确。
5. `SessionRetentionTest` 扩展：`coveredThrough` 条件（未覆盖的过期轮不删）。

**真机验证清单**

1. 连续对话 20+ 轮：状态行命中率应长期 90%+，回落只在压缩点出现。
2. 压缩点：出现「📦 正在整理上下文…」，气泡不出现压缩内容；「进行中的事」页出现条目（含日记 id）。
3. 陈旧性：条目里的绝对日期 + 块首两句文案是否让模型正确对待过期状态（构造"感冒已好"场景观察是否归档）。
4. 手动改记忆/归档条目：下一轮模型是否知道（看它的回答是否体现），且状态行**不出现回落**。
5. 清空对话（勾选/不勾选）、保留天数删除、冷启动恢复。
6. 断网触发压缩失败：回答不受影响，提示可重试/放弃，放弃后不再重试。
7. 备份导出/恢复后 `buffer_items` 完整；冻结快照恢复后自动重建。

## 11. 风险与不变量（实现时逐条守住）

1. **通知只能追加、位置固定**（否则每轮多付一次未命中）。
2. **合并必须先于裁剪**（`planWindow → compact → merge → buildContext`），否则含通知的轮被裁掉会丢信息。
3. **冻结快照只在合并点刷新**；合并是回落流程的一部分 ⇒ 滞后上界 = 一个窗口周期或一次冷启动（不会永不刷新）。
4. **注入渲染是纯函数**：无相对时间、无动态排序、无"当前时间"。
5. **压缩永不阻塞回答**；失败不推进水位线（自愈）。
6. **`update_buffer` 仅压缩轮可写**（应用侧拦截）。
7. 升级时**两处一次性前缀变化**（手册新增 `update_buffer` 描述、新增 `[3]` 块）——预期，写进发布说明。
8. 行为变化需写进使用说明：**模型新写入的记忆/状态会先进对话，下一次上下文整理才并入注入块**（记忆页与「进行中的事」页始终显示最新）。

## 12. 明确不做

- 不做自动 TTL / 自动归档（用户手动管理）。
- 不自动写日记（只给「存入日记」按钮）。
- 不做模型侧即时写入（`update_buffer` 仅压缩轮，且需通过指令触发）。
- 不做只增原文日志（改用"挂相关日记 id"替代）。
- 不做独立提示词的压缩调用（走同一链路保缓存）。
- 不做"只给索引、需要时取全文"的两段式。
- 不改编辑重发/删除单条的回滚语义（工具与已整理内容都不回滚）。

## 14. 实现补充（2026-09-17 编码时的偏差，已落地）

方案在实现中做了四处微调，都与本文档其余部分一致，仅记录差异以免日后误读：

1. **`PrefixSnapshotStore` 放在 `core/storage/`**（与 `ChatSessionStore` 同目录，同款"临时文件 + 改名"写法），不放在 `core/agent/`。
2. **`markPrefixSignature` 没有实现**：合并引起的前缀变化不需要重置基线——回落原因由压缩流程用 `reasonOverride` 显式标注（`RESET_COMPACTED`），而 `lastPrefixSignature` 照常更新为新指纹，不会产生额外回落。
3. **"批次太小"的语义收紧了**：`buffer_compact_min_chars` 以下**不压缩但照常推进水位线**（视为"不值得记"）。原因：若只跳过不推进，保留天数清理会被这批永久卡住（第三条件永远不满足），而正常回落批次（约 16 轮）几乎总是超过阈值。**自愈只保留给"调用失败/用户放弃"**（由 `collectLeftovers()` 从会话快照文件补齐，最多 30 轮）。
4. **新增 `update_buffer` 的 `noop` 参数**：模型判断"这批确实没什么可记"时也要调用一次（`{"noop":true}`），压缩流程据此推进水位线，避免同一批被反复重试。

另外三处实现细节值得记住：

- `Session.planWindow` 里 `charWeight()` **一次算好**（它要读图片文件做 base64），因此比原先反复调用 `buildContext` 的实现**更省**，不是更贵。
- 压缩失败的提示是**非阻塞**的（聊天页一条可操作横条 + 「重试/放弃」），不是模态弹窗——压缩发生在发消息那一刻，模态会挡住回答。
- 整理阈值/上限等设置项在**设置 → 进行中的事**子页；清理后的"省略"只作用于注入文本，**一条数据都不删**（用户手动管理，无自动 TTL）。
