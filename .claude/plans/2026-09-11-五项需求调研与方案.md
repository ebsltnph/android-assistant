## 1. 设置页加「点悬浮球是否打开语音」开关

### 调研

- `feature/floating/FloatingPanelActivity.kt:512` `LaunchedEffect(autoVoiceRequested)`：延迟 450ms → 读 `panelVoiceMode.first()`（ime/system/remote）→ `startVoiceByMode(m)`。

   - 也可在 `FloatingBallService` 侧读设置决定 `autoVoice` 传值（服务里读 DataStore 需协程，面板侧读更简单，且面板本来就是读取方）。

## 2. 语音识别「说完停顿时间」改长 / 可配

### 调研
- 远程识别：`core/speech/RemoteVoiceRecorder.kt:128` `SILENCE_MS = 1_400L`，能量检测（`SPEECH_RMS=1200`）连续静音 1.4s 自动结束；总时长上限 `MAX_MS = 45_000L`；预录缓冲 0.6s；有「完成」按钮可手动结束。
- 系统听写：`core/speech/PanelVoiceController.kt` 注释明确写了**故意不设** `EXTRA_SPEECH_INPUT_*_SILENCE_*`（部分厂商引擎设了会"永不结束"），且内置 8s 看门狗（`STALL_TIMEOUT_MS`）。
- 键盘语音（ime 模式）：停顿完全由输入法决定，App 无法控制。
- 设置页目前**没有**任何语音时长相关设置。

### 方案
1. `SettingsStore` 新增 `voice_silence_ms`（Int，**默认 2500**，范围 1000–6000，UI 步进 500 或用输入框）。
2. `RemoteVoiceRecorder.start(..., silenceMs: Long)` 参数化（常量退化为默认值）；`ChatViewModel`/面板调用处传入设置值。
3. 顺带把 `MAX_MS` 45s → 60s（停顿变长后，总时长更容易被截断）。
4. 设置页「悬浮球语音输入」区域加一条「说完停顿」下拉/输入：1.0s / 1.5s / 2.0s / 2.5s / 3.0s / 4.0s / 5.0s，并说明"仅对远程识别生效"。
5. 系统听写（system）：**默认不动**。可选高级项（见 Q6）：传入 `EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` + `EXTRA_SPEECH_INPUT_POSSIBLY_COMPLETE_SILENCE_LENGTH_MILLIS`，同时把看门狗超时放宽到 `max(8s, silence + 6s)`，避免引擎"永不结束"时被看门狗误杀。
6. 备份字段同步。

### 风险
- 停顿太长 → 用户说完要干等；3s 以内体感尚可，5s 已经明显。建议上限 6s 并配「完成」按钮提示。
- 系统听写的静音参数是**厂商相关**，荣耀实测该引擎本身就静默失效，参数无意义；其他机型可能有效也可能卡死。

## 3. 聊天页删除单条对话（一次一组输入+输出）

### 调研
- 现在能"删"的只有：`清空对话`（全部）和 `withdrawForEdit`（仅**最后一条**用户消息，供编辑重发）。
- `Session` 存 `ChatMessage` 的扁平队列；`ChatViewModel._messages` 存 UI 气泡。
- **映射关系不对等**（关键）：
  - 会话历史里一轮 = `user(占位/原文)` + `[工具中间轮: assistant(调用行) + user([结果])] × N` + `assistant(最终回答)`；
  - UI 里一轮 = 1 个用户气泡 + 1 个助手气泡（工具轮折叠进助手气泡的 `segments`）。
- 另外 `writeDiaryNow` / 识屏结果回填会产生**只有助手消息**的"轮"。
- `Session.trim()` 现在按 `messages.size > maxTurns * 2` 截断 → 一次带 2 轮工具的对话会吃掉 3 个"轮"的额度，"10 轮"其实名不副实。

### 方案：把 `Session` 重构成「轮（Turn）」模型
```kotlin
class Session {
    data class Turn(val id: Long, val user: ChatMessage?, val assistant: MutableList<ChatMessage>)
    private val turns = ArrayDeque<Turn>()      // 完整历史（受上下限裁剪，见 §5）
    fun beginTurn(id: Long, user: ChatMessage?)
    fun appendAssistant(id: Long, msg: ChatMessage)
    fun deleteTurn(id: Long)                    // ← 需求 3
    fun removeLastTurn()                        // 编辑重发沿用
    fun replaceLastAssistant(text: String)      // 重做沿用
    fun contextForRequest(min: Int, max: Int): List<ChatMessage>   // 见 §5
}
```
1. `ChatUiMessage` 增字段 `turnId: Long`，`ChatViewModel` 按轮记账；每个 UI 气泡都能反查到轮。
2. 新 API `deleteTurn(turnId)`：
   - UI：移除该 `turnId` 的**全部**气泡（含带图气泡）；清理 `regenerateMessages` / `imageBase64ByMsgId`；
   - 会话：移除该轮的全部消息（含工具中间轮的 `[调用]`/`[结果]`）；
   - 流式中禁用；返回是否成功（用于 Toast「已从上下文移除」）。
3. UI：用户/助手气泡外侧操作行加 🗑 图标（`Icons.Filled.DeleteOutline`，30dp 同现有图标风格）。**已确认：要二次确认**——弹窗写明"仅从上下文与界面移除；已执行的提醒/日记/记忆等不会回滚"，确认后 Toast「已从上下文移除」。
4. 语义（按你的要求）：**不回退工具副作用**——已创建的提醒/已写入的日记/已记录的记忆都保留，只让这条不再出现在上下文与界面里。
5. 同步在浮动面板加同一按钮（两个界面共用 `ChatViewModel`，保持一致）——默认加，如不想要告诉我。

### 缓存影响（必须知道）
删除中间某一轮会让**该位置之后的所有缓存前缀失效**（一次性）。删完继续对话会从新位置重新累积。这无法避免，属于用户主动操作的合理代价。

### 风险
- 需要把 `Session` 的调用点（全部集中在 `ChatViewModel`，共 20 处左右）全部改成轮语义；`Agent.route(history = session.all)` 改为 `session.contextForRequest(...)`。
- 与 §5 的裁剪策略必须同时实现（都在 Session 里），建议合并为一个改造阶段。

## 4. 识图完全走聊天通道 + 删除静默调用

### 调研（现状：两条独立通道）
| 入口 | 调用 | 通道 |
|------|------|------|
| 聊天页 `+` 上传图片 → `sendWithImage` | `VisionAnalyzer.analyzeStream` | 独立：`Capability.VISION` 档案 + `SCREEN_SENSE` 提示词 + **单轮** messages（无历史/无工具/无思维链） |
| 悬浮面板识图模式输入 → `quickSendVision` | 同上 | 同上 |
| 悬浮面板 3 个按钮（提取/翻译/总结）→ `analyze(key)` | `VisionAnalyzer.analyze`（非流式） | 同上；结果经 `quickAnalyzeResult` 预烤成"用户+助手"一对消息塞进会话 |
- 会话里图片只留占位文字：`"[📷 屏幕截图]\n" + text`（`ChatViewModel:326/430`）。
- **静默调用**确认存在：`handleVisionRecordInBackground()`（`ChatViewModel:456`）在视觉回复完成后，若用户文案像记录请求（`intentRouter.looksLikeDiaryRequest`），会**再跑一次完整的隐藏工具回路** `agent.silentReply(...)`（`Agent:99`），让主模型调 `write_diary`；失败则兜底原文入日记。
- `WriteDiaryTool` 已支持 `image_paths`，但只接受路径包含 `diary_images` 且文件存在的路径（防模型编造）。
- 截图文件在 `cacheDir/screensense/`（7 天清理），不在 `diary_images/`，所以现在必须靠静默调用落盘转存。

### 方案（2026-09-11 确认：**同一条通道，仅"换模型"**）

核心：**不变的是通道，变的是"这一轮用哪个档案"**。
文本轮 → `Capability.CHAT` 档案；带图轮 → `Capability.VISION` 档案；其余（提示词结构、历史上下文、工具回路、流式/思维链渲染、重做/编辑/删除）**完全一致**。

1. **模型选择下沉为"每次请求一个参数"**：
   - `Agent.route(..., preferVision: Boolean)` → `AgentResult.ChatRequested(messages, capability)` → `chatReplyFlow(messages, capability)` / `chatStream(messages, capability)`；
   - `ChatViewModel` 判定 `hasImage = 本轮用户消息 content 含 image_url` 后传入；
   - `providerRegistry.profileFor(VISION)` 未指派时本来就回退默认档案 ⇒ **只配了一个带图模型的用户零配置可用**（此时对话/识屏同一档案，缓存最优）。
2. **图片作为 `ContentPart.image` 进会话消息**：`ChatMessage("user", [text, image])`，不再写 `[📷 屏幕截图]` 占位文字。`streamReply` 已处理 `reasoningContent` ⇒ 思维链自动显示；工具回路自动可用。
3. **丢掉识屏独立提示词**（已确认）：任何"额外的 system 块"都会插进消息数组里破坏缓存前缀，所以不采用。图片轮的用户文案 = 用户输入本身（或快捷按钮的预置指令）。
   - 删除 `PromptStore.SCREEN_SENSE` 键与设置页「识屏提示词」入口（避免"改了没效果"的死开关）；旧备份里的该键自动忽略。
   - **新增三个可编辑提示词**（设置 → 高级设置 → 提示词），对应面板三个快捷按钮：
     `SCREEN_ACTION_EXTRACT`「识屏·提取文字」/ `SCREEN_ACTION_TRANSLATE`「识屏·翻译」/ `SCREEN_ACTION_DESCRIBE`「识屏·总结内容」；默认值 = 现 `instructionFor` 文案 + "只输出结果、不要多余解释"。
     点按钮 = 用该提示词作为本轮用户文案 + 图片，走普通对话回路（面板输出区直接看到流式结果与思维链）。
   - `ScreenSenseStarter.instructionFor()` 改为从 `PromptStore` 读取（传 promptStore 或由面板侧 `promptStore.prompt(key)` 取）；`PromptsAdvancedPage` 的过滤条件去掉 `SCREEN_SENSE` 后自动列出新三项。
   - （可选，P4 附带）关键词/工具路径已解析出 `ScreenAction` 但被丢掉；可透传到面板**预选**对应按钮（默认仍不自动发送，保持"截图不自动发消息"的既有交互）。
4. **图片落盘 + 告知模型路径**：发送时把图存到 `filesDir/diary_images/img_<时间戳>.jpg`（`ImageUtils.saveToFilesDir` 已有），文案附"图片已保存到 <路径>"；模型即可自己 `write_diary(..., image_paths=[路径])`。
5. **删除静默调用**（你确认）：删 `handleVisionRecordInBackground()` 与 `Agent.silentReply()`（确认无其他调用方后整函数删除）。带图记录**完全依赖**主模型的 `write_diary`。副作用：模型漏调时记录会丢——若日后发现偶发丢失，可低成本加回"本地关键词写库兜底（不产生模型调用）"。
6. **`VisionAnalyzer` 整类退役**（`analyze` / `analyzeStream` / `buildMessages` 全部不再有调用方）；`GUIDE_TEXT` 常量移到 `ChatViewModel` 附近；`AppContainer` / `ChatViewModel` 构造参数同步清理；`quickAnalyzeResult` 这个"预烤一轮"的入口退役。
7. **图片统一压成 JPEG**（宽 ≤1280、q80）再 base64：截图现在是 PNG（base64 常 1–3MB），每轮重发很占上传时间；JPEG 约 150–300KB。注意：**token 数由分辨率决定，与压缩格式无关**。

### ⚠️ 必须处理的新问题：历史图片发给纯文本模型会 400
图片留在历史里之后，**后续文本轮也会带上这张图**。若「对话」档案是纯文本模型（如 DeepSeek），下一轮必然 HTTP 400。
建议规则：
- **当前轮的图片始终发**（用户明确意图；不支持就让 API 报错，并给明确提示"当前模型不支持图片输入，请到 模型配置 指派识屏模型/勾选支持图片"）；
- **历史消息里的图片**：当目标档案未勾选"支持图片输入"（`supportsVision=false`）时，自动替换为 `[（历史图片）]` 文字占位（**只改本次请求，不改会话存储**）；
- 设置页「识屏（视觉）模型」状态卡片补一句：未勾选「支持图片输入」→ 历史图片不会带给它。

### 缓存影响（你问的"如何保证命中"）
缓存是**按"服务端 + 模型"分**的，所以：
- **最省心也最省钱的配置：把「对话」和「识屏」指派成同一个档案**（你现在的用法应该就是"一个带图的聊天模型"）→ 所有轮次共用同一条不断延长的消息数组，命中率最高。
- 若两者是不同提供商/模型：图片轮与文本轮的缓存是**两套**，只能在"同模型的轮之间"累积。夹花使用时，文本轮仍能在"上一个文本轮之前"的前缀上命中（因为数组结构完全一致），只是中间那一轮之后要重算。
- 建议设置页加一行状态："识屏档案 = 对话档案（缓存最优）/ 识屏使用 X（缓存与对话独立）"。

### 4.5 历史图片保留策略（回答"哪个最保命中"）
严格按命中率排：**不改历史消息 = 全部保留**最优。
- **全部保留**：每轮数组都是上一轮的延长 ⇒ 前缀 100% 命中；
- **替换更早的图片为占位**：只在**新增图片那一刻**造成一次"从被替换位置起"的前缀失效（此后重新稳定），代价有限；
- 但图片 token 由分辨率决定、每轮都会重新计数/重发，且上下文重置（U→L）时本来就要全量重算一次。
- **建议**：默认"保留最近 1 张"，设置页给三选一（全部 / 最近 3 张 / 最近 1 张）+ 说明"保留越多越贵；替换只在新增图片时产生一次缓存失效"。若你把命中率绝对优先于成本 → 选"全部保留"。（**已确认：默认最近 1 张 + 三选一**。）

### 收益 / 风险
- 收益：带图轮获得完整上下文、工具调用、思维链；模型自己整理日记；少一次隐藏调用；图片消息可重做/编辑/删除。
- 风险：
  - 视觉模型（若与对话模型不同）要能吃下完整助手系统提示词 + 工具手册；能力弱的视觉模型可能在工具协议上表现差 → 建议它就是你的主力带图聊天模型。
  - 图片 token / 上传体积（用 §4.5 保留策略 + §5 上下限一起控）。
  - `maxTokens 4096` 不变（推理模型思考占配额，已验证）。
  - 面板 3 按钮从"非流式一次出结果"变成流式对话，按钮期间要禁点（复用现有 `analyzing` 状态）。

## 5. 提高对话缓存命中率

### 5.1 关键发现：现在最大的问题是 `messages[3]`
`PromptBuilder.buildChatMessages()` 产出：
```
[0] system  外壳 + 用户提示词        （几乎不变，可缓存）
[1] system  长期记忆块               （追加式，偶尔变）
[2] system  工具手册（静态文本）      （永不变）
[3] user    "当前时间：2026年8月25日 星期一 14:03\n可用日记标签：…"   ← 每分钟都变
[4..n]      对话历史
```
提示词缓存按**最长公共前缀**命中。`[3]` 每分钟变一次 ⇒ **`[4..n]` 整段对话历史每次都重新计算**，只有 `[0..2]` 能命中。
所以：轮转窗口只是第二重问题；**把"当前时间"从中间挪到尾部/消息内，收益比上下限窗口更大**。

### 5.2 时间戳（你的问题：历史消息是否带时间）
- 现状：**不带**。`ChatDto.ChatMessage` 只有 `role/content/reasoningContent`；只有 `[3]` 那条全局"当前时间"。
- 方案（2026-09-11 确认：**只给用户消息打**）：
  - 用户消息（前缀）：`[2026-08-25 14:03] 帮我看下这句话`；
  - 时间取"消息创建时刻"，写一次就固定 ⇒ 对缓存友好（前缀不变）；当前时间由**最新一条用户消息**的时间戳天然提供 ⇒ `[3]` 那条全局"当前时间"消息**取消**（这正是最大的缓存杀手，见 §5.1）。
  - 助手消息不打时间戳（也避免模型模仿 `[...]` 前缀污染输出）；助手回复的时间可由紧随其后的用户消息时间推断，够用。
- 需要同步改 `PromptBuilder`：删除 `[3]` 易变消息里的时间（标签词汇表挪去 `[1]`，见 §5.3），并更新 `SYSTEM_SHELL_SUFFIX` 里"请忽略第一条当前时间消息"的说明为"用户消息开头的 `[日期 时刻]` 是发送时间" ⇒ **一次性**缓存失效。
- 工具中间轮（model 的 `[调用]` 原文 + `[结果]` 消息）**不打时间戳**：它们是协议文本，且必须与发送时逐字节一致才能保证前缀命中（现在已经是：`exchanges` 直接来自同一次构造）。

### 5.3 重新分层（按"易变程度从前往后"）
```
[0] system  外壳 + 用户提示词
[1] system  工具手册 + 日记标签词汇表     ← 标签改了才失效（设置页手动改，极少）
[2] system  长期记忆块                    ← 移到手册之后：记忆追加只影响其后
[3..]       对话历史（含时间戳、工具中间轮、图片）
```
理由：标签词汇表从"每次请求重建的易变块"变成"手册的一部分"（内容只在用户改设置时变），记忆块后移让记忆变动的影响面更小。

### 5.4 上下文长度上下限（你的方案）
- 语义：用户在设置页填 **下限 L / 上限 U**（轮）。
  - 会话轮数 ≤ U：整段发送（上下文自然 +1）；
  - 追加新轮后 > U：**只发最近 L 轮**，并把 Session **物理裁剪**到 L 轮（UI 的聊天记录不受影响，仍完整显示）。
  - 于是发送序列呈 `L → L+1 → … → U → L → …`，每段区间内前缀严格"上一次的延长"，**区间内每轮都能命中前面全部缓存**；每个区间只在重置点失效一次。
- 默认值建议：**L=5，U=20**（现在只有"10"一个值；取 L=5/U=20 兼顾记忆与缓存）。
- 迁移：旧键 `conversation_max_turns` 的值作为 **U 的初始值**，L 默认 `min(5, U)`；新键 `conversation_min_turns`。
- 校验：`2 ≤ L ≤ U ≤ 100`；UI 用两个输入框 + 文案说明 + 显示"当前：X 轮 / 上限 U"。
- 备份字段同步（`BackupSettings`）。

### 5.5 已确认要做的两项增强
1. **缓存命中可观测**（已确认）：解析响应 `usage`——OpenAI 系 `prompt_tokens_details.cached_tokens`，DeepSeek `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。加到 `Usage` DTO（`ignoreUnknownKeys=true`，加字段安全），在聊天页底部显示"输入 3210 tokens · 缓存命中 2800（87%）"。
   - 非流式：`Agent.chatStream` 的响应里本来就有 `usage`；需要把最后一个 chunk 的 usage 传出来（新增 `ReplyEvent.UsageInfo` 或并入 `Final`）。
   - 流式：需要请求带 `stream_options: {"include_usage": true}`；部分中转站可能 400 → 复用 `effortSafeCall` 同款"按 baseUrl|model 记忆的降级重试"（不认就永久不发，App 重启后重探一次）。
   - 这是验证整套缓存策略是否真的生效的唯一手段。
2. **字符软上限**（已确认）：轮数 ≠ token（一次 `read_webpage` 截断 6000 字就顶十几轮闲聊）。在轮数上下限之外再叠一条按**字符数**（近似 token）的约束：
   - `contextForRequest` 先按上限 U 裁轮，再从头丢弃直到总字符 ≤ 软上限（保底至少保留最近 1 轮）；
   - 设置页显示"当前上下文约 N 字 / 上限 M"；软上限默认给一个宽裕值（如 24000 字，约 12k token 量级），可改或关闭；
   - 注意：字符裁剪与"下限 L"可能冲突——规则定为"**软上限优先于下限**"（安全第一），并在 UI 文案里说明。
3. `regenerate` 的过期上下文问题：现在重做用请求快照 `regenerateMessages`，会话被删改/裁剪后重做会发出**过期上下文**。Session 重构后改为"用当前会话重建最后一轮请求"。

## 7. 其他架构层面建议（详细版 + 2026-09-11 决策）

### 7.1 缓存分层的三个细节（需求 5 的延伸）— ✅ 认可，直接做
1. **块顺序按"最稳定→最易变"排**：`[0]系统 → [1]工具手册+标签词汇表 → [2]长期记忆 → [3..]对话`。记忆（模型随时可 `write_memory`）挪到手册之后，记忆变化时不必重算手册那 1–2k token。
2. **标签词汇表并入静态块**：`buildVolatileContext()` 现在每轮重建"时间+标签"；时间挪进用户消息时间戳后，标签很少变（只有用户改设置时），并进 `[1]` 即可。`ToolRegistry.manual()` 保持纯静态，由 `PromptBuilder` 在拼装时追加标签段，职责不变。
3. **同一轮回复内前缀本来就是冻结的**（澄清）：`chatReplyFlow` 的工具循环只在尾部追加 `assistant/user(结果)`，不会在工具轮之间重建系统/记忆/手册块 ⇒ 一次回复的 2–4 轮工具调用天然全部命中前面的缓存。副作用：本轮 `write_memory` 写入的记忆要到下一轮才出现在前缀里（并造成一次前缀失效），即"上下文里的记忆块"与数据库相差一轮，属正常。
4. **不做**：按窗口段冻结记忆快照（收益极小，且会让模型看到的记忆滞后最多 U 轮，可能重复写入）。

### 7.2 `regenerate` 用请求快照 — ✅ 认可，改（P2 一起做）
- 现状：`sendText` 里 `regenerateMessages[streamingId] = result.messages` 存**整份请求快照**（含当时的时间块/记忆/历史），重做时原样重发。
- 问题：① 删除/裁剪/记忆更新后重做发的是**过期上下文**，界面与实际不一致；② 重做新产生的工具中间轮（`outcome.exchanges`）被丢弃，而会话里还留着**上一次**的旧工具轮 → 会话历史自相矛盾并一直带下去；③ Map 只增不减（仅"清空对话"清理），快照可能含 base64 图片。
- 改法：删掉 `regenerateMessages`。重做 = 取最后一轮的 user 消息，用**当前 Session** 重建请求再跑一遍，跑完整体替换该轮的 assistant 段（工具轮一起换）。P4 之后图片轮同样可重做。

### 7.3 会话持久化 — ✅ 只做轻量版，且**不进备份**
- 现状：`Session` + `_messages` 全在内存，进程被杀（MagicOS 后台清理激进）即清空，只剩 `ConversationLog` 的记录。
- 决策：**轻量方案**——消息列表 + 轮结构序列化成 JSON 存 `filesDir`（如 `chat_session.json`），启动时恢复；**不落 Room、不进备份**（会话本身是随时可丢的内容）。
- 附带决策：**加定时清理**，只保留最近一段时间的会话快照（不必长期记录）。
- 额外收益：恢复的历史若与前缀逐字节一致，服务端缓存可能仍在 TTL 内 ⇒ 也可能命中缓存。

### 7.4 图片文件生命周期 — ✅ 认可，改（P4 的前置，否则带图记录会静默丢图）
- 现状坑：`AssistantApplication.cleanupCaches()` 每次启动删除 `filesDir/diary_images` 下**所有未被 DB 引用**的文件；而 `WriteDiaryTool` 只接受路径含 `diary_images` 且文件存在的 `image_paths`。若把聊天图片直接存进 `diary_images`，用户没让记录 → 下次启动被清理 → 会话里留死路径，模型之后引用会被静默过滤（正文照写、图没了）。
- 改法：聊天/识屏图片存**独立目录** `filesDir/chat_images/`；`WriteDiaryTool` 放宽为"`diary_images` 或 `chat_images` 下存在的文件"，真正写入日记时把文件**复制**进 `diary_images`（此后受 DB 引用保护）；清理规则：`chat_images` 超过 N 天或已被会话窗口淘汰的删除。
- 顺带：聊天上传图片现在**完全没落盘**（内存 base64 + `imageBase64ByMsgId` 40 条 LRU）；P4 落盘后 LRU 退役，内存也省。

### 7.5 状态可见性 — ✅ 认可，改
- 聊天页标题行右侧加极简状态：`上下文 8/20 轮 · 约 3.2k 字 · 上次命中 87%`，点开看细节（上次请求输入/命中 token、是否触发软上限裁剪）。
- 理由：荣耀 logcat 看不到 App 日志（项目平台注意事项），"把状态显示到界面"是这里一贯的验证手段；上下文/缓存对用户完全不可见，容易产生"它怎么忘了"的困惑。

### 7.6 面板与聊天页一致性 — ✅ 1/2/4 顺带做，③加附件预览
- ① 面板输出区只渲染 `messages.takeLast(30)`（聊天页是全部）⇒ 删除很靠前的消息在面板无视觉反馈。
- ② 面板操作按钮是 26dp **竖排图标列**（复制/编辑/朗读/重做），加"删除"成第 5 个，气泡只有 0.9 屏宽，需确认观感。

- ④ 删除二次确认弹窗用 Material3 `AlertDialog`，面板是透明 Activity + 自定义深色玻璃主题，弹窗配色要单独确认（历史踩过"透明 Scaffold 致正文全黑"）。

### 7.7 能力语义与设置页文案 — ✅ 认可，改

### 关键实现细节（与原始方案的偏差）
1. **图片只存路径不存 base64**：`Session.Turn.imagePath`，组装请求时才读文件转 base64（`Session.imagePartOf`）。好处：省内存、可直接持久化、"保留最近 N 张"只需把老轮的 `imagePath` 置空（不改写历史消息内容）。
2. **当前轮的图永远发**；**历史图片**在目标档案没勾"支持图片输入"时自动替换成文字占位（`Agent.stripHistoricalImages`）——避免纯文本对话模型在带图轮之后每轮都 400。
3. **`usage` 抓取**：流式请求带 `stream_options.include_usage`；不认识的厂商按 `effortSafeCall` 同款"400 → 去掉参数 + 按 baseUrl|model 记忆"降级。
4. **`Agent.silentReply` 与 `SilentResult` 已删除**，`VisionAnalyzer` 整类删除（`AppContainer`/`ChatViewModel` 构造参数同步清理）。
5. 未做：关键词/工具路径的 `ScreenAction` 透传预选（列为可选，未实现）；记忆块按窗口段冻结（已否决）。

## 11. 滑动卡顿排查与优化（2026-09-11，第二轮）

### 11.1 测量方法（关键教训）
`adb shell input swipe` 注入滑动**不可用**：每次注入都在设备上启动一个 `app_process` JVM 抢 CPU，把卡顿/帧时长数据污染得一塌糊涂（曾得出 300–700ms 整帧、66–95% jank）。**只有用户手动滑动 + `dumpsys gfxinfo` 汇总才可信**。流程：
1. `dumpsys gfxinfo <pkg> reset` 两次（间隔 3s，丢掉切页面/沉降帧）；
2. 确认 `Total frames rendered: 0`（同时证明"界面静止不重绘"）；
3. 让用户**只滑动 8–10 秒**、不切页面不点按钮；
4. 立刻 `dumpsys gfxinfo <pkg>` 读汇总。

### 11.2 归因结论（760 帧纯净滑动数据）
- 50th 帧时长 **23ms**（中位数就超 16.6ms 预算）、90th 113ms、janky 37%；
- **Slow UI thread = janky 帧的 100%**；**Slow issue draw commands = 0**；**Slow bitmap uploads = 0**；
- **GPU 50th/90th/95th = 3/3/3ms**（760 帧里 667 帧正好 3ms）；
- ⇒ **绘制与 GPU 无罪，瓶颈 100% 在 UI 线程的组合/测量/布局**。第一轮"绘制录制 11.7ms 是瓶颈"的判断**作废**（那个数字来自被污染的注入测量）。
- 机制：LazyColumn 快速滑动时每帧必须**同步**把新进屏的条目组合+测量出来 ⇒ 成本 = 「每个条目的固定组合开销 × 每帧新进屏条目数」。对应三条主观描述：越快越卡、密集短条目卡、长日记稀疏不卡。
- 本 ROM 的 `dumpsys gfxinfo <pkg> framestats` **不输出逐帧 CSV 段**（只有汇总），拿不到阶段拆分 ⇒ 无法进一步归因。

### 11.3 已实施的裁剪（观感不变或轻微取舍，用户已确认可接受）
1. `RichMessageText`：无公式消息**不再套 `BoxWithConstraints`**（SubcomposeLayout＝每条纯文字消息白付一次子组合）；
2. 聊天气泡 + 面板气泡的**渐变 Brush / 描边 Color / RoundedCornerShape 提到文件级常量**；
3. 划词容器由「每个正文段一个 `SelectionContainer`」改为「每条消息一个」；
4. 日记条目**标签药丸（FlowRow + 每标签 2 节点）→ 单行纯文字**；
5. 日记条目操作入口 `IconButton + 矢量 Icon` → **轻量 28dp 文本「⋯」按钮**，菜单只在展开时进组合；
6. 清掉 `MainActivity` 重复的 `requestNotificationPermissionIfNeeded()`。

⚠️ **未做的**：原计划的"长按条目弹菜单"**不可行**——长按会和划词（`SelectionContainer`）抢手势，长按正文只会选中文字、菜单打不开。改为保留显式小按钮。

### 11.4 复测结果（同条件 10 秒纯滑动，857 帧）
| 指标 | 改前 | 改后 |
|---|---|---|
| 50th 帧时长 | 23ms | 22ms |
| 90th / 95th / 99th | 113 / 150 / 200ms | **69 / 93 / 133ms** |
| janky | 37.0% | **28.8%** |
| ≥150ms 长停顿 | 47 帧 | **8 帧（-83%）** |
| ≥200ms 帧 | 15 帧 | **0 帧** |
| Slow draw commands / GPU | 0 / 3ms | 0 / 3ms |

**结论**：裁剪有效，收益集中在**长停顿**（"顿一下"级别的卡顿基本消掉）；但**中位帧仍 22ms 超预算**，说明还剩一笔**每帧恒定**的成本（疑似滚动时整屏绘制命令重新录制，也在 UI 线程上），在无法拿到 profiler trace 的前提下无法继续归因。
再往下只能"盲砍"（去掉划词 / 砍渐变描边圆角 / 压缩条目高度），收益不确定、外观缩水 ⇒ **用户决定就此收尾**。
